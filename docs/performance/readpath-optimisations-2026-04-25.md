# Read-path optimisations: measured before/after

> **Snapshot doc.** Captured 2026-04-25 against AU index. Not auto-
> generated — written once to record the impact of one specific
> round of perf work so future engineers can see *why* the changes
> shipped, not just *what* changed. The "live" benchmark numbers
> live in [`benchmarks.md`](benchmarks.md) and are regenerated by
> `scripts/run-benchmarks.sh`.

## TL;DR

Five hot-path optimisations landed in commits `ac3c9df` (Rust) and
`9ac9f91` (C++ builder). Two of them produce measurable wins on the
existing AU index without any rebuild:

| What | Where it shows up | p95 change |
|---|---|---:|
| **`find_admin` no-double-call in `query_with_lang`** | `/reverse?lang=…` | **−7.5 %** |
| **Deferred string hydration in autocomplete heap** | `/autocomplete?q=…` (broad prefixes) | **−32.1 %** |

The other three (zero-alloc ASCII compare, `axum::Json`,
`addr_points.bin` cell sort) are on cold paths or require an index
rebuild — they're documented in the [methodology](#methodology) section
but don't have HTTP-level numbers in this snapshot.

## Why this doc exists

A reviewer one quarter from now should be able to look at the
"hot-path perf" commits and decide *whether to keep them*. That
requires evidence that the changes actually bought us something —
not an assertion that "it should be faster." This doc captures the
evidence, the test methodology, and the exact reproduction
commands so a follow-up engineer can re-run and either confirm or
challenge the numbers.

## Headline results

### Criterion: FST autocomplete (`server/benches/autocomplete.rs`)

Run on AU index, 8-prefix fixture set, `--sample-size 30
--measurement-time 2 --warm-up-time 1`. Numbers are
criterion-reported medians of 30 samples each.

| Prefix | Walk size | Baseline (`d8883fc`) | After (`9ac9f91`) | Δ |
|---|---:|---:|---:|---:|
| `"s"` (1 char) | up to 10 000 keys | 2.15 ms | 1.33 ms | **−38 %** |
| `"sy"` (2 char) | thousands | 58.1 µs | 36.7 µs | **−37 %** |
| `"syd"` (3 char) | hundreds | 13.2 µs | 9.79 µs | **−26 %** |
| `"sydn"` (4 char) | dozens | 9.58 µs | 7.37 µs | **−23 %** |
| `"sydney"` (full word) | dozens | 9.78 µs | 7.46 µs | **−24 %** |
| `"bondi beach"` (two words) | 1 | 2.90 µs | 2.92 µs | ~0 % |
| `"wagga wagga"` (rural) | 1 | 2.78 µs | 2.61 µs | −6 % |
| `exact_match("sydney")` | 1 (FST `get`) | 1.52 µs | 1.45 µs | ~0 % |

The pattern matches the optimisation's shape: the bigger the FST
walk, the bigger the win. Pre-optimisation `heap_push_bounded`
allocated one `String` per visited candidate (10 000 allocations
for a 1-char prefix); post-optimisation only the surviving `limit`
items materialise their names. Narrow prefixes (multi-word, rural
unique tokens) and exact-match are unchanged because the heap
visits very few candidates either way.

Limit also affects the win shape — a higher `limit` keeps more
items in the heap (= more `String`s would have been allocated
pre-fix) but post-fix the cost is still bounded by `limit`:

| `limit` | `"s"` baseline | `"s"` after | Δ |
|---:|---:|---:|---:|
| 5 | 1.99 ms | 1.28 ms | −36 % |
| 10 | 2.15 ms | 1.33 ms | −38 % |
| 50 | 2.32 ms | 1.42 ms | −39 % |

### k6 HTTP: end-to-end load test

5 scenarios × 8 VUs × 20 s, run in sequence. ~1.1 M requests per
pass; one pass at baseline (`d8883fc`), one at HEAD (`9ac9f91`).
Baseline RPS: 8 418 / pass; HEAD RPS: 8 884 / pass (~+5 %
throughput overall).

| Endpoint | p50 baseline | p50 after | p50 Δ | p95 baseline | p95 after | p95 Δ |
|---|---:|---:|---:|---:|---:|---:|
| `autocomplete_broad_ms` (`q` ∈ s/sy/b/m/br) | 2.56 ms | 1.73 ms | **−32.6 %** | 3.62 ms | 2.46 ms | **−32.1 %** |
| `autocomplete_ms` (mixed prefixes) | 0.49 ms | 0.48 ms | −1.3 % | 2.89 ms | 2.04 ms | **−29.3 %** |
| `reverse_lang_ms` (`?lang=zh`) | 0.50 ms | 0.47 ms | **−5.8 %** | 0.79 ms | 0.73 ms | **−7.5 %** |
| `search_ms` | 0.50 ms | 0.49 ms | −1.2 % | 0.77 ms | 0.76 ms | −0.5 % |
| `reverse_ms` (no lang) | 0.48 ms | 0.48 ms | −1.0 % | 0.79 ms | 0.79 ms | −0.4 % |

The interpretation is straightforward:

- `autocomplete_broad` and `autocomplete_mixed` p95 confirm win #4
  (autocomplete heap dedup). Mixed shows a smaller p50 because
  narrow prefixes (already cheap) drag the median down; the tail
  is where broad-prefix latency lives.
- `reverse_lang` p50 −5.8 % / p95 −7.5 % confirms win #1
  (`find_admin` is no longer called twice on `?lang=`).
- `reverse` and `search` deltas inside ±1 % confirm we did **not**
  regress unrelated paths.

## Methodology

### Hardware

- **Apple M1 Max**, 10 cores (8 perf + 2 eff), 64 GB RAM, macOS 15.7
- Single-machine local test: server and load generator on the same
  host, communicating over the loopback interface

This is a developer-laptop measurement, not production. Numbers
will be different on AWS — typically Graviton 4 / x86-64-v3 servers
will be **slower per core** than M1 Max but with more cores
available. Production-fleet numbers should re-validate against an
EC2 build host.

### Software

- Rust **1.95.0** (rustc 2026-04-14), `--release` profile (LTO on)
- C++ builder unchanged for this measurement (the local AU index
  was built with the previous builder; the addr-points cache-sort
  win #5 isn't reflected here — would need a rebuild)
- k6 via Docker (`grafana/k6:latest`) so the host doesn't need a
  k6 install
- Criterion 0.5 with `--sample-size 30 --measurement-time 2
  --warm-up-time 1` (reduced from defaults to keep each pass under
  three minutes)

### What's compared

Two commits, both already on `main`:

- **Baseline**: `d8883fc` — *"Rust: ban `.unwrap()` everywhere"*.
  Last commit before the perf work; functionally equivalent to the
  pre-perf state.
- **After**: `9ac9f91` — *"Builder: sort `addr_points.bin` by S2
  cell"*. Tip of the perf series.

The five optimisations between those two commits:

1. `find_admin` dedup in `query_with_lang` (`lib.rs`)
2. Zero-alloc `eq_ignore_ascii_case` / `contains_ignore_ascii_case`
   in housenumber lookup (`lib.rs`, `address_points.rs`)
3. `axum::Json` instead of `to_string()` + tuple response
   (`main.rs`)
4. Deferred string hydration in `Autocomplete`'s heap
   (`autocomplete.rs`)
5. C++ builder sorts `addr_points.bin` by S2 cell for read-side
   cache locality (`build_index.cpp`)

Wins #1 and #4 dominate the measured numbers. Wins #2 and #3 are
real but smaller and don't show clearly above noise on this
hardware (the bench resolution at p95 is ~50 µs; #2/#3 are sub-µs
per request). Win #5 is invisible until the local index is
rebuilt by the new C++ binary — see [unmeasured](#unmeasured)
below.

### Comparison-running pattern

To get clean before/after without polluting the working tree:

```bash
# 1. Set up a worktree at the baseline commit (does not disturb HEAD)
git worktree add /tmp/geocoder-baseline d8883fc

# 2. Copy the bench scripts into the worktree (they didn't exist
#    at baseline)
cp -r scripts/bench /tmp/geocoder-baseline/scripts/
cp scripts/bench-http.sh /tmp/geocoder-baseline/scripts/

# 3. Add the [[bench]] entry to baseline Cargo.toml
#    (autocomplete bench is registered in HEAD, not baseline)
# (one-line edit — see scripts/bench/k6-readpath.js for the source)

# 4. Run baseline pass
cd /tmp/geocoder-baseline
GEOCODER_INDEX_DIR=/abs/path/to/data/index \
    cargo bench --bench autocomplete -- --sample-size 30 \
    --measurement-time 2 --warm-up-time 1

./scripts/bench-http.sh --label baseline-d8883fc \
    --index /abs/path/to/data/index

# 5. Save the JSON report somewhere outside the worktree before
#    teardown — it's gitignored
cp tests/regression/reports/http-bench-baseline-d8883fc.json \
    /abs/path/to/main/tests/regression/reports/

# 6. Tear down worktree
cd /abs/path/to/main
git worktree remove --force /tmp/geocoder-baseline

# 7. Run HEAD pass — bench-http.sh auto-diffs against the most
#    recent prior report it finds in tests/regression/reports/
./scripts/bench-http.sh --label head-9ac9f91
```

The criterion `--save-baseline` / `--baseline` flags are the more
ergonomic way to do this for the autocomplete bench specifically;
the worktree dance is needed for HTTP because the bench scripts
themselves didn't exist at the baseline commit.

## Unmeasured

This snapshot does **not** capture:

- **Win #5 (`addr_points.bin` cache sort)**. The local AU index
  was built before the C++ change shipped. Rebuilding the index
  with the new `build-index` binary should produce a 10–30 % win
  on dense-urban `/reverse` queries (cache-locality on the
  9-cell addr scan). A follow-up snapshot after a planet rebuild
  would surface this.
- **Cold-cache latency**. The numbers above are "warmed" — the
  laptop's disk cache holds the 1.4 GB AU index across passes.
  Production cold-start (first query after a server restart) is
  not reflected.
- **Network and TLS overhead**. The k6 test hits `localhost:13580`
  over plain HTTP. Real client RTT, ALB termination, and TLS
  handshakes add to the wall-clock.
- **Concurrency at scale**. 8 VUs is comfortably below saturation
  for an 8-core M1 Max. Scaling tests at much higher concurrency
  may show different bottlenecks (allocator contention, OS file-
  cache pressure).
- **Non-AU traffic**. The local AU index has ~1 country worth of
  admin polygons and FST keys. Worldwide load with ~250 country
  partitions stresses different paths.

## Reproducing this snapshot

The two bench harnesses live at:

- `server/benches/autocomplete.rs` (criterion)
- `scripts/bench-http.sh` + `scripts/bench/k6-readpath.js` (k6 via
  Docker)

For the criterion bench, point it at any built AU index:

```bash
GEOCODER_INDEX_DIR=/abs/path/to/data/index \
    cargo bench --bench autocomplete
```

For the HTTP bench (Docker required):

```bash
./scripts/bench-http.sh --index /abs/path/to/data/index --label myrun
```

Both write JSON summaries into
`tests/regression/reports/`; `bench-http.sh` runs a `jq` diff
against the most recent prior report automatically.

## Numbers worth re-checking

Anyone touching the read path in a way that could regress these
wins should re-run and compare:

- `Autocomplete::heap_push_bounded` and any caller of
  `heap_into_sorted_hits` — that's where win #4 lives. If you find
  yourself adding a `String` to the per-push tuple, that's likely
  a regression.
- `Index::query_and_admin` — internal helper introduced for win
  #1. If a future change makes `query_with_lang` call
  `find_admin` again, expect `reverse_lang` p95 to climb back to
  ~0.79 ms.
- `find_addr_point_in_country` and `AddressPointIndex::find_by_housenumber`
  — both rely on byte-wise case-insensitive compare helpers
  (`contains_ignore_ascii_case`, `str::eq_ignore_ascii_case`).
  Reintroducing `to_ascii_lowercase()` on every visited candidate
  brings back the dense-city allocation storm.
